# Analysis Boundaries and Threat Model

This document defines what each layer of ThreatFlux Binary Analysis does, what
it does not establish, and how to place the library behind a safer
untrusted-file boundary.

## The four layers

| Layer                           | Input                                                 | Output                                                         | What the output means                                            |
| ------------------------------- | ----------------------------------------------------- | -------------------------------------------------------------- | ---------------------------------------------------------------- |
| Format detection                | Leading bytes and, for Java archives, ZIP entry names | <code>BinaryFormat</code>                                      | The input matched a recognized signature or fell back to raw     |
| Parsing                         | Entire byte slice                                     | Metadata, sections, symbols, imports, exports                  | The parser reconstructed the structural fields it implements     |
| Disassembly and graph analysis  | Architecture plus available code bytes                | Instructions, basic blocks, control-flow/call graphs, metrics  | A best-effort reconstruction from bytes and discovered functions |
| Security and entropy heuristics | Parser metadata, names, imports, sections, and bytes  | Findings, categories, hardening flags, entropy, weighted score | Triage signals generated by fixed rules and thresholds           |

Success at one layer does not validate the next layer. In particular:

- a detected magic does not prove the whole file is well formed;
- a successful parse does not prove the file is safe to load or execute;
- a disassembled byte sequence does not prove the intended runtime path;
- a reconstructed graph does not prove complete reachability;
- a low score or empty finding list does not prove benign behavior.

## Parser boundary

<code>BinaryFile::parse</code> is synchronous and owns a copy of its input.
Format parsers convert dependency output into owned project types before
returning. Memory-map construction is separately exposed as unsafe because the
caller must uphold backing-file stability.

Rust bounds checks and the crate's error types reduce risk, but the crate does
not promise that every malformed input is panic-free, bounded in work, or safe
from bugs in transitive parsers. Treat parsing as adversarial computation.

Current format boundaries include:

- unrecognized non-empty input is accepted as raw data;
- Mach-O support is for thin images, not fat/universal containers;
- Java class support validates only the fixed header and does not expose the
  version or decode the constant pool, members, attributes, or bytecode;
- JAR support enumerates class entry names but does not decode classes;
- WebAssembly modules receive full wasmparser validation before selected
  sections/imports/exports are exposed, but the crate does not publish decoded
  instruction semantics or a virtual-address entry point;
- PE symbol extraction is limited to COFF records and Mach-O extraction to
  nlist records; stripped images can expose no symbols and richer debug-symbol
  reconstruction is out of scope;
- signatures are not cryptographically verified.

Before Goblin parses thin-image load commands, the parser bounds load-command
and section counts, validates that section records fit their segment commands,
checks that dylib and rpath strings are contained and NUL-terminated in their
commands, validates symbol/string-table ranges and nlist string indexes with
host-sized checked arithmetic, and checks the raw `LC_MAIN`/`__TEXT` operands
used to calculate the entry-point address. Before Goblin materializes Mach-O
imports or walks an export trie, it also checks dyld bind/export ranges,
opcodes, indexes, expanded record/name budgets, cycles, and arithmetic.
Unsupported or malformed encodings fail closed. Export trie traversal is
limited to 128 levels; this is a compatibility limit, not a claim that accepted
exports are trustworthy.

The full input is copied. <code>Section::size</code> describes the virtual or
in-memory span, while <code>Section::file_size</code> describes bytes backed by
the file at <code>Section::offset</code>. <code>Section::data</code> retains only
an inline preview for eligible file-backed sections no larger than 1 KiB, and
some formats retain no preview at all. Built-in analysis resolves checked
file-backed section ranges against the full owned bytes; preview storage is an
output convenience, not an analysis or input-memory limit.

Disassembly requires the end-exclusive base-address plus byte-length range to
fit in <code>u64</code>. Inputs that would wrap an instruction address fail
instead of publishing non-monotonic addresses or branch targets.

## Disassembly boundary

Disassembly is a separate, feature-gated operation:

- iced-x86 accepts x86 and x86-64;
- the Capstone adapter accepts x86/x86-64, ARM/ARM64, MIPS32/64, and
  PowerPC32/64;
- <code>DisassemblyConfig::max_instructions</code> bounds decoded instruction
  count for a direct operation;
- <code>AnalysisConfig::max_analysis_size</code> rejects oversized inputs in
  <code>BinaryAnalyzer::analyze</code>/<code>analyze_binary</code> and also
  bounds bytes considered by its high-level disassembly path;
- <code>AnalysisConfig::max_disassembly_instructions</code> independently caps
  the total instructions returned by that high-level path and defaults to
  10,000.

Direct <code>BinaryFile::parse</code> has no configured input-size policy.
Passing a pre-parsed file to <code>analyze_binary</code> applies the analyzer
limit only after the original parse and copy have already occurred.

The high-level path resolves checked file ranges from executable-section
metadata into <code>BinaryFile</code>'s full bytes. It applies the independent
byte and instruction budgets and can skip a section whose range is invalid or
not file-backed. If all attempted executable sections fail, it returns an
error. An empty instruction list does not prove that the input contains no
executable code.

Instruction categories and flow targets are derived from mnemonic/operand
representations. They are not an intermediate language, emulator, or formal
semantics.

## Graph-analysis boundary

Control-flow and call-graph construction depend on discovered function symbols
or a limited entry-point fallback. Stripped binaries, missing entry points,
invalid file ranges, and analysis budgets can therefore yield empty or partial
graphs.

The implementation can skip individual function failures and continue, but
returns an error if every discovered function fails. Below the configured
limits this partial-success behavior is deterministic. Both low-level analyzers
default to at most 10,000 discovered functions and 1,000,000 decoded
instructions in total; control-flow analysis also defaults to 10,000
instructions per function. Advanced control-flow analysis additionally defaults
to 10,000 retained loops and 1,000,000 aggregate loop-body memberships (a block
present in two loops counts twice). Exceeding one of these limits returns an
error rather than a truncated graph. These counters are not a complete CPU or
memory ceiling.

High-level base control flow does not implicitly enable cognitive complexity or
retained advanced-loop details. If base and enhanced output are both requested,
the analyzer performs one graph-construction pass and derives both result views
from it. Dominator nesting depths and dominance intervals are indexed once per
graph so complexity and loop queries do not repeatedly walk long dominator
chains.

Indirect-call analysis records <code>CallGraphEdge::callee</code> as
<code>None</code>; it does not resolve function pointers or virtual dispatch.
This is distinct from a real target at address zero. Tail-call analysis
recognizes only selected final direct jumps and consumes the already-decoded
last instruction rather than running a second disassembly pass or retaining all
decoded instruction vectors until the end. Dynamic loading, import-thunk
following, self-modifying code, exception edges, and runtime-generated code are
not resolved. Complexity, loop, reachability, and recursion fields describe only
the reconstructed graph.

<code>CallGraphConfig::max_labeled_call_depth</code> limits breadth-first depth
labels only. It does not limit edge extraction or reachability classification.

Use graph output for navigation and prioritization, not proof of behavior.

## Security-heuristic boundary

<code>SecurityAnalyzer</code> applies fixed rules to:

- exact imported API names;
- selected substrings in section and symbol names;
- writable-and-executable sections;
- parser-derived hardening flags.

The weighted 0–100 score is local to this implementation. It is not CVSS, a
malware probability, or an exploitability score. Imported cryptographic,
network, filesystem, or registry functions are often normal application
behavior. Conversely, static imports and names are easy to hide.

Hardening fields are also parser-dependent approximations. A false field can
mean “not detected,” not necessarily “definitively absent.” Missing-hardening
findings and score penalties are limited to native ELF, PE, and Mach-O inputs;
Java, WebAssembly, and raw inputs are not penalized for inapplicable native
flags. Repeated equivalent import, section, and symbol records contribute one
finding per rule. No Authenticode, Mach-O code-signing, or JAR signature
verification is performed.

Entropy and packer-name results use fixed thresholds and a short signature list.
High entropy occurs in benign compressed/encrypted assets, and packed code can
avoid those signatures.

## Built-in structural limits

To prevent compact shared tables from expanding into unbounded validation or
owned output, ELF, PE, Mach-O, Java/JAR, and WebAssembly parsing enforce these
public hard limits per parse:

- <code>MAX_PARSED_RECORDS</code>: 100,000 structural/output records;
- <code>MAX_NAME_BYTES</code>: 4 KiB for one copied name;
- <code>MAX_OWNED_NAME_BYTES</code>: 32 MiB across copied names.

JAR central-directory preflight has an additional 50,000-entry ceiling and
rejects ZIP64 and multi-disk archives. Exceeding any hard parser ceiling returns
an error. These limits bound specific amplification paths; they are not a total
heap, CPU, recursion, or wall-time budget.

## Untrusted-input deployment

For a service or ingestion pipeline, establish limits outside this crate:

1. Accept bytes into a bounded upload or stream. Do not read an unbounded file
   into memory first.
2. Reject input larger than the application's explicit maximum, then check the
   final in-memory length again to avoid metadata/read races.
3. Set <code>AnalysisConfig::max_analysis_size</code> to the same or a lower
   limit when using <code>BinaryAnalyzer</code>.
4. Allowlist expected parsed formats and reject <code>Raw</code> unless it is an
   intentional input type.
5. Run parsing and analysis in a low-privilege worker process with a read-only
   filesystem, no network access, and OS-enforced CPU, memory, file, process,
   and wall-time limits.
6. Kill and replace a worker that exceeds its budget. The library itself has no
   timeout or cancellation API.
7. Store error details and samples as sensitive data. Do not reflect parser
   diagnostics or file contents directly to an untrusted client.
8. Keep the crate and its transitive parsing/disassembly dependencies updated
   and monitor RustSec advisories.

A file-size check belongs before parsing:

```rust
use std::{fs, io};
use threatflux_binary_analysis::BinaryFile;

const MAX_INPUT_BYTES: u64 = 32 * 1024 * 1024;

fn parse_bounded(path: &std::path::Path) -> Result<BinaryFile, Box<dyn std::error::Error>> {
    let metadata = fs::metadata(path)?;
    if metadata.len() > MAX_INPUT_BYTES {
        return Err(io::Error::new(io::ErrorKind::InvalidData, "input too large").into());
    }

    let bytes = fs::read(path)?;
    if bytes.len() as u64 > MAX_INPUT_BYTES {
        return Err(io::Error::new(io::ErrorKind::InvalidData, "input too large").into());
    }

    Ok(BinaryFile::parse(&bytes)?)
}
```

This example limits file size but does not add CPU/memory isolation; use a
worker boundary for hostile samples.

## Pattern matching

<code>PatternMatcher</code> limits both match count and aggregate owned result
bytes. <code>MatchConfig::max_output_bytes</code> defaults to 16 MiB and counts
the cloned pattern metadata and matched bytes stored in both
<code>SearchResults::matches</code> and its category buckets. A search fails
before constructing the next match when that limit would be exceeded; it does
not return a partial result.

This output limit does not bound scan time. Large custom rule sets or long
patterns can still require substantial CPU work, so retain a worker-level time
limit for attacker-controlled data.

## Memory mapping

The memory-map API is useful for bounded reads, but parsing a mapped slice still
copies it. Its constructors are unsafe: keep the underlying file immutable for
the entire mapping lifetime and do not map a path an untrusted party can
replace, truncate, or mutate.

<code>AdvancedMmap</code> rejects file-backed huge-page requests. Populate is
Linux/Android-only and memory locking is Unix-only; unsupported platform
requests return configuration errors, and supported lock requests can still be
denied by the OS.

## Archive and compression limits

JAR detection opens ZIP metadata, iterates entries, and rejects more than
50,000 entries. It does not decompress class bodies. The compression helper
supports a caller-selected expanded-output ceiling; its convenience function
uses a 64 MiB default.

For untrusted compressed input, call <code>decompress_with_limit</code> with an
application budget and retain worker-level time/memory controls. Expanded-byte
limits do not by themselves bound CPU time or nesting in other archive formats.
